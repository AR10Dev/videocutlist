# Performance and security dependency review

As of 2026-09-28. This is a source review, not a vulnerability scan, performance measurement, or recommendation to change dependencies.

| Subject | Evidence and interpretation |
| --- | --- |
| Go patch level | The local [`go.mod`](../go.mod) declares `go 1.26.0`. The [Go release history](https://go.dev/doc/devel/release) records a `net/http` fix in 1.26.7 and cgo/compiler/runtime/`debug/elf`/`os` fixes in 1.26.8; 1.26.8 is the newest listed 1.26 patch. [CI](../.github/workflows/ci.yml) and [release validation](../.github/workflows/release.yml) now install 1.26.8; the `go` directive remains a language/toolchain minimum. The release history does not label 1.26.7 or 1.26.8 as security releases. |
| SQLite driver and rollback | Local [`go.mod`](../go.mod) requires `modernc.org/sqlite v1.59.0` and indirectly pins `modernc.org/libc v1.75.7`. The [driver's v1.59.0 module file](https://proxy.golang.org/modernc.org/sqlite/@v/v1.59.0.mod) requires exactly libc v1.75.7, and its [package documentation](https://gitlab.com/cznic/sqlite/-/raw/v1.59.0/doc.go) warns downstream modules to use that exact libc version. The [tagged changelog](https://gitlab.com/cznic/sqlite/-/raw/v1.59.0/CHANGELOG.md) says the journal-rollback corruption bug in SQLite 3.53.3 was temporarily patched in driver v1.56.0; driver v1.58.0 moved to SQLite 3.53.4, containing upstream's fix, and dropped the temporary patch without changing recovery behavior. Driver v1.59.0 still embeds SQLite 3.53.4 (the transpiled SQLite is reported byte-identical to v1.58.0), **not a rollback to vulnerable 3.53.3**. [SQLite's 3.53.4 release note](https://sqlite.org/releaselog/3_53_4.html) describes fixes generically; the precise journal-rollback attribution comes from the driver's own changelog. Do not confuse this journal-rollback bug with SQLite's distinct [WAL-reset corruption bug](https://sqlite.org/releaselog/3_53_4.html), whose fix is listed among changes since 3.53.0. |
| Reported SQLite performance | The [v1.59.0 changelog](https://gitlab.com/cznic/sqlite/-/raw/v1.59.0/CHANGELOG.md) attributes Linux memory/string-routine improvements to the matched libc v1.75.7. Its [performance note](https://gitlab.com/cznic/sqlite/-/raw/v1.59.0/doc.go) reports **CPU-time ratios against native C SQLite**, not absolute speeds: unindexed `ORDER BY … LIMIT 100` over 584k rows changed from 3.0× to 2.0×, `GROUP BY` from 2.2× to 1.9×, and indexed correlated subquery from 1.6× to 1.3×, measured on linux/amd64 with Go 1.27 and SQLite 3.53.4. Separately, v1.59.0 reports pooling UDF callback contexts (1000 fewer allocations/op and 16 KB/op on its 1000-row noop UDF benchmark). These are **upstream-reported, workload-specific** results; neither the measured Go version nor the workloads establish gains for this project or its Go 1.26 CI. The changelog says non-Linux targets already had native Go memcpy/memmove and do not get the same change. |
| `golang.org/x/sys` and `x/sync` | [`go.mod`](../go.mod) directly requires `x/sys v0.48.0`, and project code imports `x/sys/unix` on [Linux](../internal/export/publish_linux.go) and [Darwin](../internal/export/publish_darwin.go). The official [module metadata](https://proxy.golang.org/golang.org/x/sys/@v/v0.48.0.mod) requires Go 1.26.0; [the module proxy's latest pointer](https://proxy.golang.org/golang.org/x/sys/@latest) currently identifies v0.48.0. SQLite v1.59.0 itself requires `x/sys v0.47.0` ([module file](https://proxy.golang.org/modernc.org/sqlite/@v/v1.59.0.mod)); the local direct requirement is higher. `x/sync v0.23.0` is published and requires Go 1.26.0 ([metadata](https://proxy.golang.org/golang.org/x/sync/@v/v0.23.0.mod), [latest pointer](https://proxy.golang.org/golang.org/x/sync/@latest)), but **it is not a requirement in this project's `go.mod`**; [`go.sum`](../go.sum) contains a checksum for v0.22.0, not evidence that v0.23.0 is installed or used by the app. An `x/sync v0.23.0` requirement does appear in [govulncheck v1.8.0's module file](https://proxy.golang.org/golang.org/x/vuln/@v/v1.8.0.mod), which is a separate tool dependency. No security fix or performance gain for the project follows solely from those version numbers. |
| `govulncheck` | The [Go team's tutorial](https://go.dev/doc/tutorial/govulncheck) prescribes `go install golang.org/x/vuln/cmd/govulncheck@latest`, then `govulncheck ./...` from the module root. The official [module proxy's latest pointer](https://proxy.golang.org/golang.org/x/vuln/@latest) currently reports `golang.org/x/vuln v1.8.0` (published September 8); its [module file](https://proxy.golang.org/golang.org/x/vuln/@v/v1.8.0.mod) requires Go 1.26.0. `@latest` is a moving target; CI now installs `@v1.8.0` for reproducibility. The [Go vulnerability documentation](https://go.dev/doc/security/vuln/) explains that the tool analyzes known vulnerabilities and reachable calls. Local scan outcomes by Go patch version are recorded below. |

**Unverified implications:** The upstream rollback fix is documented as shipped, but there is no local reproduction or database-integrity proof here. The upstream CPU figures do not quantify this application's performance. Whether a particular Go patch fixes a reachable issue, and whether a vulnerability report applies to deployed binaries, requires a project-specific assessment; this review does not claim either.

## Repository-specific corrections and priorities

| Chatlog claim | Current evidence and decision |
| --- | --- |
| Every browse row is JSON-decoded; a missing index explains browsing | [Browse](../internal/db/media.go) visits every available row, but decodes metadata only for the returned page; the available/id index already exists. Folder IDs are computed from paths, so a selective folder query requires a reviewed schema change, not a driver swap. Measure representative catalog sizes before redesigning. |
| Waveform uses `binary.Read` per sample | [Waveform](../internal/web/assets/assets.go) already uses `binary.LittleEndian.Uint32` and `math.Float32frombits`; remove this item from the proposed work. |
| Metrics latency is only the last request; `/metrics` is public | [Metrics](../internal/httpapi/metrics.go) already emit a cumulative summary (`_sum`/`_count`), not a last-value gauge. Metrics previously bypassed deployment auth; [the route](../internal/httpapi/api.go) now passes through the existing access gate while health/readiness remain public. Histograms are optional if measured latency distribution needs them. |
| The cache metadata table enables cheap hits | [cache_entries](../internal/db/migrations/004_cache.sql) is currently unused; the [preview cache](../internal/preview/cache/cache.go) FFprobes on hits and walks/sorts completed files on commit. [Timeline assets](../internal/web/assets/assets.go) walk/sort on *each lookup* and validate decoded data. Do not drop hit validation without replacing its corruption-detection guarantee, or introduce a second authoritative cache index without reconciliation. |
| Parallel scanning or `singleflight` should be added first | [Scanning](../internal/library/media/index/index.go) is sequential and re-probes unchanged files. The [shared limiter](../internal/projects/preview_limits.go) already constrains preview/assets/export/detection but not scan probes. First benchmark unchanged scans and put probes under a common resource budget; then decide whether bounded concurrency helps on actual storage. Cache-key deduplication is valuable only if concurrent misses are observed; request cancellation and failed generation must not affect other subscribers. |
| `SetMaxOpenConns(1)` is a likely bottleneck | [Database setup](../internal/db/database.go) deliberately sets one connection and connection-local PRAGMAs. Keep it until contention is measured; raising it without per-connection PRAGMAs changes correctness. |
| Jobs scheduler index misses its order | The [claim query](../internal/jobs/scheduler.go) filters by `state` and orders by `created_at,id`. The old `(state,updated_at)` index required a temporary sort; the checked-in [migration](../internal/jobs/migrations/001_jobs.sql) creates the claim-order index and drops the superseded index, including on existing installations. |

Security work not covered by a dependency upgrade: media children currently inherit the server environment (including a configured bearer token); filter sensitive variables without discarding required FFmpeg environment or sandbox media parsing in a separate worker when the threat model justifies it. A `.mp4` FIFO previously blocked the rooted open before the regular-file check. Scanning now skips known special entries, and Unix rooted opens use nonblocking mode before checking the opened descriptor; non-Unix platforms precheck file type but still need a race-safe nonblocking open to cover type swaps. Incremental scanning must not treat size+mtime as cryptographic identity: [source validation](../internal/library/media/index/index.go) currently compares only that tuple, so same-size/same-mtime rewrites remain undetectable. The cache's per-key lock map retains keys indefinitely; preserve same-key coordination if replacing it. Container read-only rootfs, capability drop, and PID limits are reasonable to validate against hardware encoders and configured mounts, not blanket safe defaults.

Rooted media opens now also compare the opened descriptor with `os.Root.Lstat` of
the final entry (`os.SameFile`) and reject final symlinks. This catches an
in-root symlink to a same-stat file and an entry changed between open and
recheck; it is not cryptographic identity or an atomic path lock. In
particular, a regular same-stat replacement *before* open still passes the
catalog fingerprint. `os.Root.OpenFile` resolves in-root symlinks even when
given `O_NOFOLLOW`, so simply setting that flag does not establish this rule.

The [local govulncheck run](https://pkg.go.dev/vuln/GO-2026-6090) with devenv's Go 1.26.5 reported three reachable standard-library findings: [GO-2026-6090](https://pkg.go.dev/vuln/GO-2026-6090), [GO-2026-6089](https://pkg.go.dev/vuln/GO-2026-6089), and [GO-2026-5972](https://pkg.go.dev/vuln/GO-2026-5972), all fixed in 1.26.6. Running the same scan with `GOTOOLCHAIN=go1.26.8` reported no vulnerabilities. CI/release now use 1.26.8; developers must also use a patched Go toolchain for production builds. Reachability analysis is not an exploit demonstration; CI will run pinned govulncheck against its own toolchain.
